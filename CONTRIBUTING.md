# Contributing Guide

Thanks for your interest in MemVault! This document explains how to get involved with the project.

## Development Workflow

We use a PR-centric collaboration model:

1. **Fork** this repository and clone it locally
2. Branch off `master`: `git switch -c feat/<short-desc>`
3. **Write tests first** (TDD) — see "Development Conventions" below
4. Implement the feature / fix the bug
5. `cargo fmt` + `cargo clippy` + `cargo test` all pass
6. Push the branch and open a PR
7. **After the PR is merged, delete the branch** — both locally (`git branch -D <branch>`) and on the remote (`git push origin --delete <branch>`). GitHub's "Automatically delete head branches" is off for this repository, so the remote branch is **not** removed by the merge; verify with `git remote prune origin`.

### Toolchain Note (Source Builds)

`memvault-core` embeds local inference via fastembed, which links a prebuilt ONNX Runtime static library. Building from source therefore needs a modern C++ toolchain — independent of which embedding provider you configure at runtime:

- **CI-verified:** Ubuntu 24.04 x86_64/ARM64 runners (GCC 13-class), macOS, Windows MSVC
- **Prebuilt runtime floor:** Linux release artifacts inherit the runner's glibc/GLIBCXX baseline, so the release workflow **pins** the GNU builds to `ubuntu-24.04` / `ubuntu-24.04-arm` (glibc 2.39) and runs a post-build gate: `objdump -T` symbol check (no `GLIBC_* > 2.39`, no `GLIBCXX_* > 3.4.33`) plus a startup smoke test (`--version` × 3, CLI save/search, MCP & Proxy stdio `initialize` on a throwaway DB). Don't switch the release runner to an older distro (link floor) **or to `ubuntu-latest`** — the 0.6.9 x86_64 build on an updated `ubuntu-latest` silently required `GLIBC_2.43` symbols and wouldn't start on glibc 2.39 systems. Any deliberate floor change must update the compatibility notes in README/README.zh-CN/docs/AGENT-INSTALL.md together with the gate
- **Known to fail:** GCC 8 (CentOS 7/8-era libstdc++, `GLIBCXX` too old) — link-time errors about missing C++20/23 stdlib symbols (`std::format`, `std::to_chars`)
- **If `cargo build` stalls at `Compiling ort-sys`:** the crate's own downloader is waiting on a stalled connection (30-minute timeout, no retry). Run `scripts/fetch-ort-cache.sh` to pre-seed its cache with curl; see §9.4 of `docs/TROUBLESHOOTING.md`
- Users on legacy distros should consume the prebuilt release binaries, Homebrew tap, or Docker image instead; last-resort workaround is switching the fastembed feature in `crates/memvault-core/Cargo.toml` from `ort-download-binaries-rustls-tls` to `ort-load-dynamic` (loads `libonnxruntime` at runtime; embedding degrades to keyword search if the shared library is absent)

## Development Conventions

### Rust Code

- `cargo +stable fmt` must produce no diff
- `cargo +stable clippy --all-targets --all-features -- -D warnings` must pass
- Test coverage: unit + integration (workspace gate: line ≥92% / region ≥90% / function ≥85%)
- Error handling: recoverable errors go through `anyhow`, domain errors through custom `thiserror` types — **no `unwrap()`** (except in tests or genuinely unreachable branches)
- Public API changes must be reflected in the corresponding section of `docs/DESIGN.md`

### Commit Messages

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

Common `type`s: `feat` / `fix` / `refactor` / `docs` / `test` / `chore` / `perf` / `ci` / `build`

### Documentation

- `docs/DESIGN.md` is the single source of truth for design — architecture/interface changes must update the relevant section
- New `docs/*.md` files must be registered in the `README.md` documentation index

## Pre-PR Checklist

- [ ] `cargo fmt` + `cargo clippy` + `cargo test` all pass
- [ ] Added an entry under `CHANGELOG.md`'s `[Unreleased]` section
- [ ] Breaking changes are noted with a `BREAKING CHANGE:` footer
- [ ] Opened an issue to discuss before writing into a new domain (reduces rework risk)
